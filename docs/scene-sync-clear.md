# Scene Sync: シーンをクリア

Editorのシーンメニュー（スマホでは「…」）、Studioの既存「…」メニューの
区切られた最下部にある「シーンをクリア」で5秒の予告を開始する。
Playerには開始操作を置かない。全端末に実行者名と予告、「キャンセル」を表示し、
同じルームのどの端末からでも取り消せる。参加者数や
StudioのEdit / Playによる制限、全員承認は設けない。重複要求で予告を延長しない。

WebXR では頭部の前に予告を描画する。予告中の controller `selectstart`
（トリガー／対応するハンド入力）はキャンセルを優先し、オブジェクトを掴まない。
XRセッションとルーム接続は維持する。実機での可読性・コントローラー／ハンド
入力は別途HMDで確認する必要がある。

## クリアの範囲

- 管理対象オブジェクト全件。背景画像の sky sphere も含む。
- オブジェクトのLoomグラフ、AudioSource、動画、アニメーション、物理実行状態。
- 選択・ロック・ドラッグ、途中の読込、Undo / Redo、オブジェクト用クリップボード。
- オブジェクトの物理／操作イベント履歴。

環境プリセット、シーン全体のBGM・Loomグラフ・物理設定・Scene Clock、
カメラ、Shell、参加者アバターは維持する。初期化前の履歴バックアップや
クリアのUndoは追加しない。既存の端末内自動保存は継続し、空の状態も保存する。

## 稼働中ルームの世代

サーバーは接続がある間だけ、ランダムな `epoch` と予告を保持する。
クリア確定時にepochを更新し、オブジェクト数と物理イベントログをリセットする。
最後の接続がなくなったら予告タイマーと世代記録を破棄する。再起動をまたぐ
永続化は行わない。

1. `welcome.sceneRoom` に `{ epoch, cleared, pending, serverTime }` を返す。
2. Webは `hello.sceneProtocol: 1` を宣言する。再接続ごとに同期をやり直し、
   完了後に `{ type: 'scene-ready', epoch }` を送る。
3. 書込み／シーン応答のpayloadに `sceneEpoch` を付ける。サーバーは
   WebSocket broadcast、個別handoff、REST、AI経路の入口で検証する。
4. `scene-clear-request` は `epoch` と一意の `requestId` を持つ。
   `scene-room` の `pending` イベントで実行者と期限を配信する。
5. `scene-clear-cancel` の `requestId` が現在の予告と一致すれば取り消す。
   期限後のキャンセルは確定済みのクリアを戻さない。
6. `scene-room` の `cleared` イベントで新世代へ移る。各端末は片付けと
   空状態の保存を行って再びreadyを送る。旧世代の送信・応答は拒否する。

非同期処理は開始時のローカル世代トークンを保持する。クリア・切断・ルーム移動で
トークンを無効化し、完了時の新世代を古い処理に付け直さない。既にアップロードした
blobや素材キャッシュの全消去はしないが、古い処理からシーンへ再登録しない。

## 再接続と端末内保存

再接続後、readyな参加者からシーンを再取得する。空のシーンも置換として適用し、
受信完了まで旧シーンを他端末へ供給しない。クリア後に追加されたオブジェクトは
現世代の内容として受け取る。再取得のタイムアウトを空状態の確定とは扱わない。

参加者がいない場合に端末内保存を読むときは「前回のシーンを復元しますか？」と
確認する。Noでは空から開始する。確認中や復元中の途中参加、切断、ルーム移動、
クリアにより処理を無効化する。稼働中ルームでクリア済みと分かっている場合は、
旧世代の保存データを復元候補にしない。

全員退出／再起動後にはサーバーにクリア記録がないため、古い保存かどうかを
サーバーから判定する保証はない。この場合もWebは自動復元せず、明示確認する。
素材の復旧可能性は既存のキャッシュ・blob TTL・参加端末に依存する。

## 旧クライアントとの互換性

クリアを実行していないルームでは、世代のないUnity・Godot・旧Web・RESTを
従来どおり受け入れる。クリア済みの稼働中ルームでは、世代なし／不一致の
書込みとシーン応答を `scene_epoch_mismatch` で拒否する。RESTは409を返す。
アバター、素材転送等の非変更通信は維持する。

WebSocketの拒否応答は `{ type: 'error', error: 'scene_epoch_mismatch', message: ... }`。
旧Web（基準main `c0f944f`）には汎用errorハンドラがあり、書込み時に更新を促す
トーストを表示する。一方、このチェックアウトのUnity Editor / RuntimeとGodotの
Presence受信処理には `error` の表示処理がない。サーバーは拒否を返すが、これらの
ネイティブUIで利用者が失敗を認識できる保証はない（コード確認、実機未検証）。

旧クライアントの表示そのものを新しい予告・クリアUIへ更新することはできない。
旧Webは再読み込み、エンジンクライアントは上記プロトコル対応が必要。
全員退出で記録が消えた新しいルームは従来互換の状態へ戻る。
これは書込み権限や認証の追加ではなく、古い世代の自動再送を防ぐ境界である。

## デプロイ後にメニュー項目が見つからない場合

Scene Syncはバージョン付きURLではないES modulesを動的に読む。古いStudioの
モジュールと新しい共通UIが混在すると、常設クリアボタンは消える一方、メニューに
クリアが追加されない。nginxでは `/scenesync/` と `/assets/js/scenesync/` 配下の
HTML・JS・MJS・CSSだけに `Cache-Control: no-cache` を付け、保存した応答を
再利用する前に再検証する。ディレクトリURLは解決後の `index.html` が対象になる。
内容が同じファイルはETag / Last-Modifiedによる304応答で再利用できる。
GLB・動画・画像・スプラットなどの素材、`/presence/`、他のページやvendor資産の
キャッシュ方針は変えない。`no-store` ではなく、応答本体の保存は許可する。

この設定は開いているページを強制更新せず、UI・操作・IndexedDB・localStorageも
変更しない。次の読込では変更がなくても再検証の通信が発生するため、通信遅延の
影響は受ける。オフラインやサーバーに到達できない状態では再検証に失敗し、
キャッシュだけでのページ再読込や、まだそのページで読み込んでいないモジュールの
利用ができない場合がある。既に読み込んだコードはそのまま動作するが、ルーム同期や
未読込素材など、元から通信が必要な機能は通信状態に依存する。

この設定を受信する前のキャッシュは、通常の再読み込みでも残る場合がある。
初回だけキャッシュを使わない再読み込みが必要になることがあるが、端末内シーンを
保存しているIndexedDBやlocalStorageを消す必要はない。実画面で項目がない場合は、
URL・Shell・読み込んだモジュール・配信された応答ヘッダーも確認して原因を切り分ける。
ローカル `dev:web` は `no-store` のため、通常の開発起動だけではこの混在を再現できない。

## ローカル検証

```sh
npm ci
npm ci --prefix apps/presence-server
npm run dev:web
npm run test:scene-clear
npm run test:e2e:scene-clear
```

既定はWeb `127.0.0.1:8888`、Presence `127.0.0.1:8787`。
競合時は `WEB_PORT` / `PRESENCE_PORT` を指定して起動し、ブラウザ試験にも
`AFJK_WEB_ORIGIN` / `AFJK_PRESENCE_URL` で同じ宛先を指定する。
`AFJK_CHROMIUM_PATH` でChromiumの実行ファイルを指定できる。
ブラウザsandboxとTLS検証を無効化しない。試験はloopbackの専用ルームのみを使い、
結果とスクリーンショットを `logs/scene-clear-browser-smoke/` に保存する。
XRのブラウザ代替試験はHMD実機試験ではない。
